# SQLite and credential-vault recovery

Applies to the supported **local SQLite file** deployment. Do not point a rehearsal at live services. Backups contain tenant data, password hashes, sessions and ciphertext; restrict access even without the key.

1. Record the release/commit, resolved database path, migration history, and the ID of a dedicated non-production canary credential and its tenant. Record the **secret manager version ID** of `ALOAPI_VAULT_KEY` used to create that credential, not the key itself. Store the key/version separately under a different access policy. Never pass the key on the command line or paste it into logs. Disable shell tracing. Do not generate a replacement key during restore.
2. On the DB host with the matching checkout and supported Node version, run `node scripts/vault-recovery.mjs backup /absolute/path/live.db /protected/new-backup-dir`. The new directory must not exist. SQLite's online backup API copies a consistent snapshot including committed WAL pages; **never copy only a live `.db`, discard a WAL, or combine WAL files from different snapshots**. If backup fails, quarantine the incomplete directory and retry to a new one. Encrypt the snapshot in secure backup storage. Keep a checksum in an authenticated backup inventory.
3. Restore **a copy** of `snapshot.db` under a new private directory on an isolated host, verify the inventory checksum, and disable network egress, workers, provider callbacks and mail. Do not start ALOAPI yet. Supply the original key via your private secret manager environment. Do not source an untrusted `.env`.
4. Run `node scripts/vault-recovery.mjs verify /isolated/snapshot.db CANARY_TENANT CANARY_RECORD_ID`. This opens read-only, checks SQLite integrity, foreign keys, schema against the checked-in migration history, and authenticates/decrypts the selected canary without displaying its value. Repeat for each tenant/key generation under recovery; verify the same record ID with a different tenant **fails**. Review `_prisma_migrations.migration_name` against the inventory. A wrong or missing key, schema drift or any failure is a stop condition. Successful decryption of one row does not prove every row is recoverable.
5. Compare tenant counts, membership bindings, and operator access in the isolated copy; run authorized and non-member API acceptance checks there before promotion. Never send real mail or process restored queued jobs during a drill. Review stale sessions, OAuth grants, and outstanding approvals before re-enabling traffic.
6. For a production restore obtain owner sign-off, stop all writers, take a fresh backup of the current database **and its matching key version**, and preserve it as rollback evidence. Switch configuration to the separately verified restored file; do not overwrite the original or move individual WAL files. Verify health, read-only tenant checks and audit continuity first. If checks fail, stop writers and point back to the preserved database and its matching key. Reconcile writes after the recovery point before reopening traffic.

Without the matching key AES-GCM ciphertext cannot be recovered. Restore the original secret-manager version or have the provider owner reissue the affected credentials. Do not reset or migrate production to diagnose key loss.
